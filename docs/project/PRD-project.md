# Pinklin Phase 1 — Project PRD（會員與商業核心）

> 本文件是 `spec.md` §13 Step 2 要求的 **PRD**（依專案工作流程放在
> `docs/project/PRD-project.md`）。它是整個 Phase 1 的範圍與需求清單（Level 1），
> 每條需求有固定編號 `REQ-NNN`，編號永不重用、不重新編號；被取代的需求以刪除線保留。
> 技術設計見 [`../ARCHITECTURE.md`](../ARCHITECTURE.md)；
> 任務拆解與進度見 [`TASK-BREAKDOWN.md`](TASK-BREAKDOWN.md)。

## 1. 產品概述

Pinklin 是一個整合「短影音平台」、「AI 一站式影片創作平台」與「會員中心」的產品家族。
**Phase 1 不做任何影片或 AI 功能**，而是先建立三個產品共用的商業底座：

- 統一的會員身分與登入
- 可設定的會員等級與權益，支援自動續費
- 推薦碼與推薦獎勵（獎勵層數由管理員設定，預設只發給直接推薦人）
- 獨立的 AI 點數錢包（非現金）
- 以 USDT 收款：使用者把 USDT（TRON TRC-20 或 BNB Chain BEP-20）轉入自己的專屬入金地址，儲值成站內 USDT 餘額，再用餘額購買會員與點數；退款也退回站內餘額。鏈上只用於入金（未來加上出金）
- 集中的訂單管理
- 完整的後台管理、資金管理與稽核

核心價值：未來的 AI Video Studio 與 Short Video Platform 可以直接沿用身分、權益、點數、訂單
與推薦，**不需要改動 Phase 1 的核心**。所有金融操作（USDT 餘額、點數、鏈上轉帳）必須可稽核、可對帳、不可竄改。

## 2. 目標與成功指標

### 目標
1. 交付可上線等級（production-oriented）的會員與商業核心，涵蓋 spec §16 Definition of Done 全部 18 項。
2. 金融完整性：USDT 餘額、點數與鏈上資金具交易安全、冪等、不可變帳本與對帳能力。
3. 資金安全：私鑰不進入應用程式主機；本期沒有任何轉給使用者或外部地址的鏈上轉帳，使用者的 USDT 一律歸集到冷錢包。
4. 可擴充：新增商品類型、權益種類、支付方式、區塊鏈、獎勵規則時不需改核心程式。

### 成功指標（驗收時量測）
- spec §16 的 18 項 DoD 每一項都有自動化測試證據（測試輸出）。
- 每日點數對帳：錢包餘額、有效點數批次總和、帳本累計三者差異 = 0。
- 每日資金對帳：資金帳本中各鏈資產餘額與鏈上實際餘額差異 = 0；所有分錄借貸平衡。
- 併發測試：同一錢包 50 個並發扣點請求、同一使用者 50 個並發餘額付款請求，結果都正確、無負數、無重複扣款。
- 冪等測試：同一筆鏈上入金被重複掃描 N 次，只入帳一次。
- 在本地環境執行 `docker compose up` 加初始化指令，即可用 Mock 鏈完成「註冊 → 入金 → 購買 → 履約 → 推薦獎勵 → 自動續費 → 管理員退款」全流程；在 staging 以測試網完成同樣流程。

## 3. 使用者與角色

| 對象 | 說明 |
| --- | --- |
| 訪客 | 未登入；可瀏覽方案、驗證推薦碼、註冊。 |
| 會員 | 已註冊使用者；擁有一個會員等級（預設 Free）、一個點數錢包、一個 USDT 餘額、每條鏈各一個入金地址、一個推薦碼。 |
| 推薦人 / 被推薦人 | 任何會員都可以是推薦人；被推薦人只能有一位直接推薦人。 |
| 創作者（預留） | 未來短影音模組的角色；本期只預留角色，不做功能。 |
| Super Administrator | 全部權限，包含管理員帳號、角色權限、冷熱錢包設定與轉出限額。 |
| Finance Administrator | 訂單、退款（退回站內餘額）、資金管理、點數調整、獎勵審核、財務報表。 |
| Member Support | 會員查詢、停權/恢復、協助處理訂單問題（不可調整金額、點數或發起退款）。 |
| Operations Administrator | 會員等級、商品、推薦規則、促銷點數發放、系統設定。 |

**關鍵原則**：會員等級（Tier）≠ 角色（Role）。等級只決定「權益」；角色才決定「授權」。

## 4. 術語

| 術語 | 定義 |
| --- | --- |
| 會員等級 Tier | Free / Standard / VIP / Creator 等可設定方案，決定權益。 |
| 權益 Entitlement | 等級帶來的能力或額度，以鍵值描述（例：`ai.credits.per_cycle = 500`）。 |
| 點數批次 Lot | 一次入帳的 AI 點數，有類型、剩餘量與到期時間；扣點時從批次扣。 |
| 點數帳本 Credit Ledger | AI 點數每一筆異動的不可變記錄。 |
| 站內 USDT 餘額 | 使用者儲值在平台上的 USDT，用來付款；是現金性質，和 AI 點數完全分開。 |
| 資金帳本 Funds Ledger | 記錄 USDT 與鏈上手續費資產的複式記帳帳本，每筆分錄借貸平衡。 |
| 入金地址 | 平台為每位使用者在每條鏈產生的專屬收款地址。 |
| 確認數 | 交易所在區塊之後又新增的區塊數；達到設定值才視為入帳。 |
| 熱錢包 / 冷錢包 | 熱錢包由簽章服務控管，本期只存放支付鏈上手續費用的 TRX、BNB；冷錢包離線保存，使用者入金的 USDT 一律歸集到這裡，只能人工轉出。 |
| 歸集 | 把各入金地址的 USDT 轉到平台冷錢包。 |
| 出金 | 把站內 USDT 餘額轉到使用者的鏈上地址；留給未來模組（D-14）。 |
| 簽章服務 Signer | 唯一持有私鑰、負責簽署鏈上交易的獨立服務。 |
| 推薦綁定 Binding | 被推薦人與推薦人的永久關係。 |
| 上線、下線、層級 | 推薦人是被推薦人的第 1 層上線，推薦人的推薦人是第 2 層上線，依此類推；反過來稱為下線（D-19）。 |
| 獎勵 Reward | 上線因下線的合格消費而獲得的獎勵記錄，每一層各一筆（以 USDT 計價，與點數、創作者收益分開）。 |
| 履約 Fulfillment | 付款完成後，依商品類型開通會員或入帳點數。 |

### 不在本期範圍
- 影片上傳、串流、AI 影片生成（spec §1、§14）。
- 創作者收益、分潤；出金（站內 USDT 餘額轉到鏈上地址）與推薦獎勵提領（D-02、D-14）。
- 法幣或信用卡付款；USDT 以外的幣種；TRON 與 BNB Chain 以外的鏈。
- 使用者自助申請退款（D-06）。
- 原生手機 App（API 需支援，App 不在本期）。
- 社群登入 / OAuth、發票與稅務收據。

## 6. 關鍵使用者旅程

- **J1 推薦註冊**：A 分享連結 → B 開啟註冊頁，推薦碼自動帶入 → B 註冊並完成驗證 → 帳號啟用，同時建立推薦綁定、點數錢包、USDT 餘額帳戶與 B 的推薦碼（REQ-010~015、REQ-060~066、REQ-080）。
- **J2 儲值**：會員選擇鏈別 → 取得自己的入金地址與 QR code → 從外部錢包或交易所轉入 USDT → 後端監聽到交易，達到確認數後入帳到站內餘額（REQ-170~173、REQ-182）。
- **J3 購買會員或點數**：選方案或點數包 → 建立訂單 → 以站內餘額付款（不足時提示儲值，入金後可自動付款）→ 履約開通會員或入帳點數 → 評估推薦獎勵（REQ-044、REQ-051、REQ-083、REQ-101~107、REQ-110~111、REQ-174~175）。
- **J4 自動續費**：到期前提醒餘額 → 到期前自動建立續費訂單並從餘額扣款 → 餘額不足時寬限期內每日重試 → 失敗則降回 Free（REQ-053、REQ-176）。
- **J5 管理員退款**：使用者透過客服提出 → 財務管理員在後台退款 → 金額立即退回使用者的站內餘額，同時收回會員權益、扣回點數、撤銷推薦獎勵（REQ-187、REQ-094、REQ-074）。
- **J6 後台調整點數**：財務管理員填寫原因與參考編號 → 錢包服務寫入調整帳目 → 產生稽核日誌（REQ-125、REQ-129）。

## 7. 需求

優先級：**M** = Must（Phase 1 完成條件）、**S** = Should（建議納入，可延後）。
被取代的需求以 ~~刪除線~~ 保留，並註明取代者。

### 7.0 平台與基礎設施（spec §2、§13）
- **REQ-001** — Docker Compose 一鍵啟動完整本地環境：API、背景工作程序、排程器、鏈上監聽程序、簽章服務（本地使用 Mock 鏈或測試網）、PostgreSQL、Redis、會員前台、管理後台、開發用郵件收件器。*(M)*
- **REQ-002** — 依環境（local / test / staging / production）載入設定；所有密鑰與敏感設定只來自環境變數，並提供 `.env.example`。*(M)*
- **REQ-003** — 所有 API 位於 `/api/v1/`，以 OpenAPI 3 描述並提供 Swagger UI；每個端點標明驗證方式、所需權限、請求驗證、回應格式與錯誤碼。*(M)*
- **REQ-004** — 統一的錯誤回應格式（機器可讀的 `code`、人可讀的 `message`、`details`）與固定的錯誤碼目錄。*(M)*
- **REQ-005** — 模組化單體：業務模組之間只能透過公開介面或領域事件互動，模組邊界由 CI 自動檢查。*(M)*
- **REQ-006** — 可靠的領域事件傳遞：在交易內寫入 outbox，提交後由背景程序派送（至少一次），消費端冪等；並提供排程任務機制。*(M)*
- **REQ-007** — 業務參數（驗證碼有效期、訂單付款逾時、點數扣抵優先序、推薦碼長度、各鏈確認數、歸集門檻、寬限期天數等）存於系統設定，後台可調整且有稽核，不寫死在程式碼。*(M)*
- **REQ-008** — 健康檢查端點、結構化日誌（含 request id），以及錯誤追蹤的掛勾。*(S)*
- **REQ-009** — 提供建立初始超級管理員的管理指令（可重複執行、不可透過公開 API 建立）。*(M)*

### 7.1 Module A — 註冊與身分驗證（spec §3）
- **REQ-010** — Email 註冊：email + username + 密碼，以 email 驗證碼完成驗證。*(M)*
- **REQ-011** — 手機號註冊：E.164 格式手機號 + username + 密碼，以簡訊驗證碼完成驗證。*(M)*
- **REQ-012** — 防止重複帳號：email（正規化、不分大小寫）、手機號、username（不分大小寫）各自全域唯一，由資料庫強制。*(M)*
- **REQ-013** — 密碼強度驗證：最小長度、常見/外洩密碼黑名單、不得與 username 或 email 過於相似；規則可設定。*(M)*
- **REQ-014** — 驗證碼管理：雜湊儲存、有效期、最大嘗試次數、重送冷卻、每個目標與每個 IP 的發送上限、使用後立即失效。*(M)*
- **REQ-015** — 註冊時可選填推薦碼；從推薦連結進入時自動帶入。*(M)*
- **REQ-016** — 帳號狀態 `PENDING_VERIFICATION`、`ACTIVE`、`SUSPENDED`、`DISABLED`；狀態轉換由後端規則控制並保留歷史。*(M)*
- **REQ-017** — 以 email、手機號或 username 加密碼登入；只有 `ACTIVE` 帳號可取得 token。帳密錯誤時不透露帳號是否存在；帳密正確但帳號被停權時，回傳明確的錯誤碼。*(M)*
- **REQ-018** — 簽發短效 JWT access token 與長效 refresh token；refresh token 每次使用即輪替，舊 token 若被重複使用，視為遭竊並撤銷整個 session。*(M)*
- **REQ-019** — 登出撤銷目前 session；使用者可登出所有裝置；帳號被停權或密碼變更時，既有 session 立即失效。*(M)*
- **REQ-020** — 忘記密碼：以 email 或簡訊寄送一次性重設碼，重設成功後撤銷所有 session；回應不透露帳號是否存在。*(M)*
- **REQ-021** — 防暴力破解：依 IP 與依帳號分別節流登入失敗，並採漸進式暫時鎖定。*(M)*
- **REQ-022** — 個人資料欄位：使用者 ID（對外為不可猜的 ID）、username、頭像、email、手機號、註冊時間、帳號狀態、會員等級、推薦碼、最後登入時間。*(M)*
- **REQ-023** — 使用者可修改允許的欄位（username、頭像）；變更 email 或手機號時，須先驗證新的 email / 手機號才生效。*(M)*
- **REQ-024** — 頭像上傳：限制檔案類型與大小、重新編碼並移除 metadata，儲存層可替換（本機或 S3 相容）。*(S)*
- **REQ-025** — 安全稽核日誌：登入成功/失敗、鎖定、token 重放、密碼變更/重設、驗證、帳號狀態變更，記錄時間、IP 與 User-Agent。*(M)*

### 7.2 授權（RBAC，spec §4、§8、§9）
- **REQ-030** — RBAC 資料模型：roles、permissions（字串代碼，例如 `wallet.adjust`）、user_roles、role_permissions；一個使用者可有多個角色。*(M)*
- **REQ-031** — 內建後台角色 Super Administrator、Finance Administrator、Member Support、Operations Administrator，並附預設權限矩陣（以 seed 建立，後台可調整；不可移除最後一位 Super Administrator）。*(M)*
- **REQ-032** — 集中的後端授權：每個 API 透過統一的權限元件宣告所需權限，未授權回傳 403；前端依權限隱藏功能只是輔助，不是防線。*(M)*
- **REQ-033** — 會員等級與角色分離：等級不得作為授權依據；一個使用者可同時是 VIP 會員、創作者（預留角色）與推薦參與者。*(M)*
- **REQ-034** — 後台管理員帳號管理：建立、停用、指派角色（需要專屬權限，全程稽核）。*(M)*
- **REQ-035** — 後台管理員二階段驗證（TOTP），所有管理員強制啟用。*(M，因後台可以退款、調整點數與修改鏈上設定，見 D-11)*

### 7.3 Module B — 會員等級（spec §4）
- **REQ-040** — 會員等級可設定：名稱、說明、狀態（啟用/停用）、顯示優先序、權益說明；預設建立 Free / Standard / VIP / Creator。*(M)*
- **REQ-041** — 等級權益以可擴充的鍵值定義（例如每期 AI 點數配額、AI 生成權限、每日使用上限）；新增權益種類不需要改資料表結構。*(M)*
- **REQ-042** — 等級定價：月費與年費方案（各為一個可販售的商品），包含會員期間長度，以 USDT 計價。*(M)*
- **REQ-043** — Free 為預設等級：沒有有效的付費會員時，使用者的權益就是 Free 的權益。*(M)*
- **REQ-044** — 購買會員：付款完成後開通，起訖時間依方案期間計算。*(M)*
- **REQ-045** — 續費：從「現在」與「目前到期時間」兩者較晚的時間點起，延長一個期間。*(M)*
- **REQ-046** — 升級：付款後立即生效；應付金額 = 新方案價格 − 舊方案剩餘價值，新期間從升級當下起算（規則見 D-04）。*(M)*
- **REQ-047** — 降級：排定在目前期間結束後生效，不退差價；開啟自動續費者於下次續費時改以新方案計價。*(M)*
- **REQ-048** — 到期自動處理：排程把到期的會員轉回 Free，套用已排定的降級，並發出事件。*(M)*

### 7.5 Module C — 推薦獎勵引擎（spec §5）
- **REQ-071** — 獎勵規則可設定：各層的固定金額或百分比與單筆上限（REQ-077）、最低合格消費金額、適用商品類型、活動期間、結算延遲天數、是否只限首購、每位被推薦人的獎勵上限、優先序、啟用狀態。*(M)*
- **REQ-072** — 合格訂單完成時，依規則產生 `PENDING` 獎勵（多條規則符合時取優先序最高的一條，不疊加），並保存規則快照與計算依據；同一張訂單在同一層只會產生一次。*(M)*
- **REQ-073** — 結算：延遲期滿且訂單沒有退款 → `CONFIRMED`（由排程處理）。*(M)*
- **REQ-074** — 退款連動：`PENDING` 獎勵轉為 `CANCELLED`；`CONFIRMED` 獎勵則新增一筆反向調整記錄（不修改原記錄）。*(M)*
- **REQ-075** — 推薦獎勵記錄獨立於 AI 點數帳本、USDT 資金帳本與（未來的）創作者收益帳本；本期只記帳，不提領（D-02）。*(M)*
- **REQ-077** — 推薦獎勵層數由管理員設定（`referral.reward_levels`，1 ~ 10，預設 1 = 只發給直接推薦人）；每條規則分層設定獎勵（各層各自為固定金額或百分比，可設單筆上限）；合格訂單完成時，對購買者第 1 ~ N 層的上線各產生一筆獎勵；上線不符資格時該層不發、不往上遞補；同一張訂單各層合計不超過實付金額；修改層數只影響之後完成的訂單（D-19）。*(M)*
- **REQ-078** — 推薦儀表板依層顯示第 1 ~ N 層的註冊數與付費數，獎勵歷史標示層級；會員只能看到下線的遮罩資料，看不到下線是透過誰加入的（D-19）。*(M)*

### 7.6 Module D — AI 點數錢包（spec §6）

- **REQ-089** — 併發安全：同一個錢包的異動依序處理（列鎖）；餘額與批次剩餘量不得為負（資料庫 CHECK 約束）。*(M)*
- **REQ-090** — 點數到期：排程把到期批次歸零，並寫入到期帳目。*(M)*
- **REQ-091** — 交易紀錄查詢：分頁，並可依類型與時間篩選。*(M)*
- **REQ-092** — 對帳：可驗證「錢包餘額 = 有效批次剩餘量總和 = 帳本累計」；每日排程對帳，發現異常即告警。*(M)*
- **REQ-093** — 錢包服務是唯一可以異動點數的程式入口；其他模組、後台操作與資料修正都必須經過它。*(M)*
- **REQ-094** — 點數包退款扣回：管理員退款點數包時，扣回該批次目前剩餘的點數（已使用的不扣），退款金額由管理員決定且不超過實付金額（見 D-06）。*(M)*

### 7.12 USDT 收款與站內餘額（D-01、D-03）

- **REQ-172** — 入帳冪等：以「鏈 + 交易哈希 + 事件序號」為唯一鍵，同一筆鏈上轉帳只入帳一次。*(M)*
- **REQ-173** — 站內 USDT 餘額：以複式記帳的資金帳本記錄（每筆分錄借貸平衡），與 AI 點數、推薦獎勵分開；使用者餘額不得為負；分錄不可修改。*(M)*

- **REQ-175** — 入金後自動付款：入金入帳後，若使用者有等待付款的訂單且餘額足夠，自動完成付款（可設定開關）。*(S)*
- **REQ-176** — 會員自動續費：開啟自動續費的會員在到期前（預設 24 小時）自動建立續費訂單並從餘額扣款；餘額不足時進入寬限期並每日重試，寬限期結束仍失敗則降回 Free；使用者可隨時關閉自動續費。*(M)*
- **REQ-182** — 入金頁與地址安全：清楚標示鏈別與代幣、跨鏈轉帳無法找回的警示、地址 QR code；所有輸入的鏈上地址（例如管理員登記的平台錢包地址）都驗證格式與校驗碼。*(M)*
- **REQ-184** — 異常入金處理：需要人工判斷的入金（例如風險篩查命中）記到暫記帳戶並進入人工處理佇列，處理結果只有入帳給使用者或沖銷，不在鏈上退回；其他金額大於 0 的入金一律直接入帳；仿冒代幣不入帳。*(M)*
- **REQ-186** — USDT 餘額與紀錄查詢 API：餘額、入金（含確認進度與鏈上交易哈希）、付款扣款、退款（退回餘額）。*(M)*
- **REQ-187** — 管理員退款至站內餘額：使用者不能自助退款；具 `refund.manage` 權限的管理員可對已購買的會員方案或點數包退款，金額不超過實付並須填原因與工單號；退款金額退回使用者的站內 USDT 餘額，與反向處理（收回會員權益、扣回點數、撤銷推薦獎勵）在同一個資料庫交易內完成；不涉及鏈上轉帳。*(M)*

### 7.13 鏈上資金營運（D-01、D-15、D-18）
- **REQ-177** — 資金歸集：入金地址的 USDT 依門檻定期歸集到平台冷錢包，必要時先由熱錢包補充手續費（TRON 的能量/頻寬或 TRX、BNB Chain 的 BNB）；歸集與手續費全部記帳。*(M)*
- **REQ-178** — 簽章服務：所有由系統發起的鏈上轉出（本期為歸集與補手續費；未來加上出金）由獨立部署的簽章服務簽署；私鑰不離開簽章服務；簽章服務自行檢查政策（只允許平台地址之間的轉帳、單筆與每日上限），即使應用程式主機被入侵也無法把錢轉出平台。*(M)*
- ~~REQ-179~~ — 管理員手動退款，以鏈上轉帳退到使用者指定地址、雙人核准。*已由 REQ-187 取代（2026-11-26，D-06、D-18）。*
- **REQ-180** — 冷熱錢包分離與限額：本期熱錢包只存放手續費資產（TRX、BNB），有低水位告警；使用者的 USDT 一律歸集到冷錢包；簽章服務有單筆與每日轉出上限；冷錢包的任何轉出都由人工操作，並在後台登記。*(M)*
- **REQ-181** — 鏈上對帳：每日核對資金帳本中各鏈資產（入金地址、熱錢包、冷錢包）與鏈上實際餘額，不一致即告警。*(M)*
- **REQ-183** — 風險篩查掛勾：入金來源地址（未來加上出金目的地址）可接入制裁名單或風險評分服務，命中時凍結並交由人工處理。*(S，見 D-17)*
- **REQ-185** — 後台資金管理：檢視各鏈入金、歸集與手續費轉出、冷錢包與熱錢包餘額、手續費資產水位、使用者 USDT 餘額與分錄、異常入金佇列，並可匯出。*(M)*

## 9. 假設與相依

- 正式環境需要郵件與簡訊供應商；本期提供抽象介面，開發環境使用 console / 本機收件器。

- 需要 TRON 與 BNB Chain 的節點存取：自架節點或付費 RPC 服務，至少各一個主要來源與一個備援。
- staging 使用測試網（TRON Nile、BNB Chain Testnet），並自行部署與正式 USDT 相同小數位的測試代幣。
- 歸集需要各鏈的熱錢包有足夠的手續費資產（TRX、BNB），由財務購入後在後台登記。
- 法務需確認：點數到期（D-05）、退款與提領條款（D-06、D-14）、資金託管與反洗錢（D-17）、多層推薦獎勵（D-19）、個資保護。
